Версия документа: 2.0  
Предмет: математика (`mathematics`)  
Источник иерархии: `VPR_4_CLASS_2027_PRODUCT_SPEC.md`  
Связанные спецификации: `MASTERY_SPEC.md` (формула `masteryScore`, интервалы 0/1/3/7)  
Код приложения этим документом **не изменяется**.

Этот файл — методический и технический источник для следующего этапа (банк, генераторы, `SkillMastery`).  
Он **не** является официальной спецификацией ВПР, демоверсией ФИПИ и **не** содержит заданий.

## Как читать статусы записей

Используются только четыре статуса происхождения записи:

| Статус | Значение |
|---|---|
| `DEFINED_BY_SPEC` | Явно сказано в ТЗ |
| `PROJECT_DECISION` | Проектное решение для тренажёра; это не формулировка ФИПИ и не официальная спецификация ВПР |
| `NEEDS_VPR_CHECK` | Нужна проверка по официальной спецификации / демоверсии ВПР-2027 |
| `PLANNED` | Запланировано ТЗ, в этой матрице ещё не заполнено |

Правило: если статус не `DEFINED_BY_SPEC`, запись нельзя выдавать за требование ВПР.

## 1. Назначение матрицы

Матрица — единый справочник:

**Математика 4 класса → раздел → тема → навык → подтип задания → уровень 1–5.**

Она нужна, чтобы задания, прогресс и рекомендации ссылались на одни и те же устойчивые сущности, а не на произвольные строки в карточках.

На матрицу будут опираться:

| Часть приложения | Зачем нужна матрица |
|---|---|
| Банк заданий | Каждое задание привязывается к разделу, теме, навыку и подтипу |
| Генераторы | Один генератор производит варианты **одного** навыка (ТЗ §18, §38). Код генераторов пока не пишется |
| `taskRepository` | Выборка по теме, навыку, сложности, источнику |
| Прогресс | Проценты и карта предмета считаются по разделам/темам матрицы |
| `SkillMastery` | Ключ учёта — `skillId` матрицы, а не текст вопроса |
| Адаптивное обучение | Приоритет слабых навыков |
| Слабые места | Режим `weak` |
| Повторение | Режим `topic` и интервалы |
| Кабинет родителя | Рекомендации вида «задачи на движение», а не внутренние id |
| Пробная ВПР | Покрытие проверяемых умений после сверки со спецификацией |

ТЗ §39 также требует колонки ФОП НОО, УМК «Школа России», типы заданий ВПР и плановое число тренировочных заданий. Эти колонки **не заполнены**: соответствующих таблиц в ТЗ нет.

Статус блока ФОП/УМК: `PLANNED`.  
Статус типов и баллов ВПР: `NEEDS_VPR_CHECK`.

### Что изменилось в версии 2.0

Версия 1.0 фиксировала **минимальные 22 навыка** как каркас карты. Этого недостаточно для банка, ошибок и повторения: часть умений была слишком широкой (`general.solve`, `logic.solve`, «время», «таблица»).

Версия 2.0 **замораживает каталог на 35 навыках**. Все 22 прежних ID сохранены. Добавлены 13 навыков, чтобы каждое умение можно было проверить отдельно. Новые навыки — `PROJECT_DECISION`, связь с ВПР — `NEEDS_VPR_CHECK`.

Код таксономии (`MATH_SKILLS`, 22 записи) **намеренно не синхронизирован** с этой версией. Синхронизация — отдельный этап.

## 2. Единые правила

Правила ниже действуют для **всех 35 навыков**. В карточке навыка повторяется только то, что специфично для него.

### 2.1. Уровни сложности 1–5

Шкала ТЗ §5 — `DEFINED_BY_SPEC`. Смысл уровней для банка — `PROJECT_DECISION`. Это **не** официальная раскладка ВПР.

| Уровень | Название | Что даём | Чего не даём на этом уровне |
|---|---|---|---|
| 1 | Разминка | Одно умение, короткая формулировка, числа и сюжет без ловушек, опора на знакомый приём | Несколько умений сразу, «лишние» данные, формат бланка ВПР |
| 2 | Тренировка | Типовое школьное задание на этот навык | Комбинация с несвязанным навыком |
| 3 | Повышенная сложность | Несколько шагов **внутри навыка**, переформулировка, нули, неудобные единицы, клетка, таблица с лишней строкой | Официальный номер и бланк ВПР |
| 4 | Формат, близкий к ВПР | Формулировка, объём данных и способ ответа максимально близки к типичному заданию ВПР 4 класса | Нельзя подписывать как «задание №… ВПР-2027». Это тренировочные задания **в стиле** ВПР, не КИМ |
| 5 | Эксперт | Для сильных учеников: комбинация с соседним навыком, оценка правдоподобности, выбор способа, нестандартная запись | Не обязателен для выставления статуса «Освоен». Нужен для статуса «Уверенный» на высоких уровнях |

Общие правила уровней (`PROJECT_DECISION`):

1. Уровень меняет **трудность внутри навыка**, а не создаёт новый навык.
2. Разрядность, переход через разряд, скобки, нули в записи, число действий — это уровень и/или подтип, не отдельный `skillId`.
3. Тренировочный банк навыка может начинаться с уровней 1–3. Уровни 4–5 описываются в матрице заранее, даже если банка ещё нет.
4. Уровень 4 не заполняется массово до сверки с демоверсией 2027 (`NEEDS_VPR_CHECK`).
5. Если в банке нет нужного уровня, адаптивный алгоритм берёт ближайший доступный. Отсутствие уровня 4–5 — не ошибка текущего банка.
6. Единственный числовой якорь генератора в ТЗ: сложение многозначных, разрядность 4, сложность 2 (§18) — `DEFINED_BY_SPEC` как пример, не как норма для всех тем.
7. Слово «средний уровень» в примере ТЗ §4 **не равно** числу 2, 3 или 4.

### 2.2. Критерии освоения

Освоение считается по истории попыток навыка (`skillId`), а не по одному верному ответу. Числовая формула — в `MASTERY_SPEC.md`. Здесь — педагогические пороги, которыми должен пользоваться банк и будущий адаптивный слой.

`PROJECT_DECISION`, согласовано с `MASTERY_SPEC.md`:

| Правило | Смысл |
|---|---|
| Один верный ответ не даёт освоения | При числе попыток &lt; 3 показатель не может считаться высоким |
| Нужна серия, а не случайность | Для статуса «Освоен» нужно не меньше 5 попыток по навыку, среди них устойчивая доля верных |
| Уровень 1 недостаточен | Нельзя считать навык освоенным, если все успехи только на уровне 1 |
| Подсказка снижает качество | Верный ответ с подсказкой остаётся верным, но не двигает статус вверх так же, как ответ без подсказки |
| Сложность учитывается осторожно | Уровни 1–5 влияют на уверенность, но не превращают одно лёгкое задание в «Уверенный» |
| Время не штрафует | Медленный верный ответ не хуже быстрого для освоения |
| Нет попыток — нет нуля | Навык без попыток не «Не освоен», а «ещё не проверялся» |

Минимальный педагогический порог **«Освоен»** для навыка:

1. Есть попытки не ниже уровня 2.
2. Не менее 5 попыток по этому `skillId`.
3. Последние попытки в основном верные (ориентир: `masteryScore` в зоне уверенного результата по `MASTERY_SPEC.md`, без обхода раннего потолка).
4. Последний зачётный успех — без опоры на полный набор подсказок как на способ решения.

Порог **«Уверенный»** — это освоение **плюс** устойчивость (§2.4). Без устойчивости «Освоен» не повышается.

### 2.3. Статусы навыка

Педагогические статусы матрицы (для ребёнка, родителя и методиста):

| Статус матрицы | Когда ставится | Чего он не означает |
|---|---|---|
| Не освоен | Навык уже проверялся, устойчивого верного результата нет | Не путать с «ещё не начинали» |
| В процессе | Есть верные ответы, но серия нестабильна или успехи только на низком уровне | Не равно освоению |
| Освоен | Критерии §2.2 выполнены | Не равно «можно больше не показывать» |
| Уверенный | Освоен и выполнено правило устойчивости §2.4 | Не официальная оценка ВПР |

Отдельно, **не статус освоения**:

| Служебная отметка | Смысл |
|---|---|
| Нет данных | По навыку нет ни одной попытки текущего ребёнка |

Соответствие коду (`MASTERY_SPEC.md` / `MasteryStatus`) — **только для следующего этапа**, код сейчас не меняется:

| Статус матрицы | Код `MasteryStatus` | Замечание |
|---|---|---|
| Нет данных | `new` | В коде это не уровень освоения |
| Не освоен | `not_mastered` | |
| В процессе | `developing` | В UI сейчас может отображаться как «Формируется» |
| Освоен | `confident` | В коде `confident` — **ниже** `mastered`. В матрице «Освоен» идёт **перед** «Уверенный» |
| Уверенный | `mastered` при выполнении gate §19 | В матрице «Уверенный» — высший статус. В коде высший статус называется `mastered` |

Это **намеренное расхождение имён**. При синхронизации UI нельзя подписать код `confident` словом «Уверенный»: в матрице «Уверенный» = устойчивое освоение.

### 2.4. Оценка устойчивости результата

Навык устойчив (статус «Уверенный»), если **одновременно**:

1. Педагогический статус уже не ниже «Освоен».
2. `masteryScore` высокий (ориентир `MASTERY_SPEC.md` §19: ≥ 90).
3. Есть серия из не менее 3 верных ответов подряд.
4. Последняя попытка выполнена **без подсказок**.
5. Среди зачётных успехов есть уровень не ниже 2; для полной уверенности желателен успех на уровне 3.
6. После интервала повторения (§2.5) навык снова решён верно. Один успех «сегодня» без повторения через 1/3/7 дней устойчивости не доказывает.

Если после статуса «Уверенный» ребёнок ошибается, устойчивость снимается: статус не выше «В процессе» или «Освоен» в зависимости от новой серии. Навык возвращается в повторение сразу (`reviewIntervalDays = 0`).

Устойчивость считается **по навыку**, не по теме и не по всему разделу.

### 2.5. Повторение ранее освоенных навыков

Освоенный и уверенный навык **не выпадает** из подготовки.

Принцип (`PROJECT_DECISION`, интервалы `DEFINED_BY_SPEC` как идея ТЗ §16 и `MASTERY_SPEC.md` §15–§17):

| Событие | Когда вернуть навык |
|---|---|
| Ошибка | Сразу (интервал 0 дней), с объяснением |
| Первый верный после ошибки или старта | Через 1 день |
| Второй верный подряд | Через 3 дня |
| Третий и следующие верные подряд | Через 7 дней |
| Перед пробной ВПР | Финальная проверка освоенных навыков, не только слабых |

Правила смеси в тренировке:

1. В обычной тренировке должен быть **хотя бы один** элемент повторения ранее освоенного навыка, если такие навыки уже есть.
2. Нельзя строить сессию только из слабых навыков, если у ребёнка уже есть освоенные.
3. Нельзя бесконечно держать на одном `skillId`: максимум 2 задания подряд одного навыка, затем другой навык.
4. Повторение идёт по **тому же навыку**, допустима смена подтипа и уровня. Не подменять навык «похожей темой».
5. Верный ответ с подсказкой не ускоряет интервал.
6. Задания `sourceType: 'vpr'` и DEMO без `skillId` не подменяют это правило: DEMO в освоение не входит.

Точные поля `nextReviewAt` и расчёт — в `MASTERY_SPEC.md`. Этот раздел задаёт **методическое** требование к банку: для каждого из 35 навыков должны существовать задания, которые можно показать повторно (другие числа / другой подтип, тот же `skillId`).

### 2.6. Правила формирования банка заданий

Банк пока **не создаётся**. Ниже — правила, по которым его нужно будет собирать.

1. Одно задание — **один** основной `skillId` из каталога 35. Второй навык можно указать только как опору (prerequisite), в `SkillMastery` он не засчитывается автоматически.
2. У задания обязательны: `section` / `topic` / `skillId`, `difficulty` 1–5, подтип, `taskType`, `sourceType`, объяснение, до 3 подсказок.
3. Подтип — обязательное поле будущей карточки. Нельзя плодить новые навыки из подтипов.
4. Для каждого навыка банк в перспективе покрывает **все** перечисленные подтипы и **все** уровни 1–5. Пока нет сверки ВПР, приоритет наполнения: уровни 1–3.
5. Не выдавать тренировочные и сгенерированные задания за официальные задания ВПР. `sourceType: 'vpr'` ставить только после появления легального основания.
6. Не копировать формулировки официальных КИМ. Уровень 4 — «в стиле ВПР», без номеров варианта.
7. Не использовать AI, сервер и внешнюю базу как источник истины банка. Offline-first: тексты и картинки в бандле.
8. `audio` для математики не назначается.
9. Несколько `TaskType` на один навык допустимы; тип — способ ответа, не навык.
10. `multipleChoice` ни одному навыку не назначается, пока это не подтвердит спецификация ВПР (`NEEDS_VPR_CHECK`).
11. Генератор (когда появится) меняет числа и сохраняет `skillId`. Один генератор — один навык.
12. Текущие 10 учебных заданий — задел только для сложения и вычитания. Это не покрытие матрицы и не вариант ВПР.
13. Плановое число заданий на навык (ТЗ §39) — `PLANNED`. До отдельного решения ориентир: не меньше 2 подтипов × уровни 1–3, без выдачи этого числа за норму ВПР.
14. Типичные ошибки из карточки навыка — методический список для объяснений и будущих тегов. Автоматически угадывать точный тип ошибки по одному ответу нельзя (`MASTERY_SPEC.md` §12–§13).

### 2.7. Что является навыком, а что нет

Навык — проверяемое умение, по которому считается освоение.

Не являются отдельными навыками:

- уровень сложности 1–5;
- `TaskType` (способ ответа);
- переход через разряд, разрядность, нули, число слагаемых;
- «с картинкой» / «без картинки»;
- формулировка конкретного примера.

Это подтипы, параметры генератора или уровень.

## 3. Правила идентификаторов

Код пока не меняется. Ниже соглашение для будущей связки.

Формат канонического ID:

```
math.<section>.<topic>.<skill>
```

Правила:

1. Только латиница, цифры и точка.
2. Нижний регистр, слова через `_`.
3. ID уникален в пределах приложения.
4. ID не зависит от названия на экране: заголовок можно переименовать, ID нельзя.
5. Три уровня после `math` соответствуют разделу, теме и навыку.
6. Короткий ID раздела: `math.calculation`.
7. Короткий ID темы: `math.calculation.multi_digit`.
8. Полный ID навыка: `math.calculation.multi_digit.addition`.
9. Краткий методический код `M01`…`M35` — только для этого документа. В данные задания пишется канонический ID, не `M01`.

Примеры:

| Уровень | ID | Название на экране |
|---|---|---|
| Предмет | `mathematics` | Математика |
| Раздел | `math.word_problems` | Текстовые задачи |
| Тема | `math.word_problems.motion` | Задачи на движение |
| Навык | `math.word_problems.motion.distance` | Нахождение расстояния |

`PROJECT_DECISION`: формат ID выбран проектом; в ТЗ формат идентификаторов не задан.

## 4. Иерархия и карта разделов

ТЗ §4 фиксирует:

```
Предмет → Раздел → Тема → Навык → Тип задания → Сложность → Тренировочные задания
```

В версии 2.0 после навыка явно следует **подтип**, затем уровень 1–5.

| Уровень | Что это | Что это не является |
|---|---|---|
| Предмет | Математика | Тема урока |
| Раздел | Крупный блок карты предмета | Одно умение |
| Тема | Устойчивый учебный участок внутри раздела | Конкретный пример (`234 + 125`) |
| Навык | Проверяемое умение, по которому считается `SkillMastery` | Уровень, тип UI, параметр генератора, подтип |
| Подтип | Вариант предъявления того же умения | Новый навык |
| Тип задания | Способ ответа (`numberAnswer`, `singleChoice`, …) | Содержание умения |
| Сложность | Шкала 1–5 из ТЗ §5 | Отдельный навык |

Единственный полный пример иерархии в ТЗ (§4) сохранён:

```
Математика
→ Текстовые задачи          (раздел)
→ Задачи на движение        (тема)
→ Нахождение расстояния     (навык)
→ Задание ВПР               (тип)
→ Средний уровень           (сложность)
```

### Как прочитан плоский список §18

В §18 блоки перечислены **плоско**. Что из них раздел, а что тема, ТЗ не расписывает, кроме примера про движение.

В §10 карта предмета показывает восемь подписей: Вычисления, Порядок действий, Величины, Геометрия, Таблицы, Текстовые задачи, Движение, Логика. «Движение» там стоит рядом с «Текстовые задачи», а в §4 движение — **тема внутри** текстовых задач.

`PROJECT_DECISION`: каноническая иерархия — §4. Пункты карты §10 — подписи для ребёнка, не отдельный справочник разделов. «Движение» в матрице — тема, не раздел.

`PROJECT_DECISION`: блоки «единицы измерения», «время», «масса», «длина», «площадь», «стоимость», «скорость» вложены в раздел «Величины». В ТЗ они соседи, не дети.

`PROJECT_DECISION`: «периметр», «площадь фигур», «симметрия», а также распознавание фигур и работа на клетчатой бумаге вложены в «Геометрию».

## 13. Ограничения для будущей Android/RuStore версии

Подробные требования магазина здесь не повторяются. Только принципы, чтобы матрица и будущий банк их не ломали:

1. **Offline first.** Задания, тексты, картинки и аудио математики должны жить в приложении, не на обязательном API.
2. **Минимум персональных данных.** Матрица и банк не содержат имени ребёнка; не добавлять в задания поля профиля.
3. **Без лишних Android-разрешений.** Контент не должен требовать микрофон, камеру, геолокацию, контакты.
4. **Без обязательного сервера в MVP.** Генерация и проверка — на устройстве.
5. **Понятный источник и права.** Не копировать официальные КИМ без основания; генераторы и собственные формулировки предпочтительнее.
6. **Картинки и схемы** — файлы в бандле (`public/images` или эквивалент), пригодные для WebView, без внешних URL.
7. **Не привязывать контент к Web-only API.** Не строить задания на `window`, браузерных плагинах, облачных формулах или сети «на каждый пример».
8. Параметры генератора должны сериализоваться в обычные данные (`generatorId` + `generatorParams`), чтобы одинаково работать в браузере и в Android WebView.
